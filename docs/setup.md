# Setup guide

Complete instructions to go from a fresh clone to a working deployment. Follow top to bottom for
a brand-new environment; the [Quick reference](#quick-reference) at the end condenses it.

## 1. Prerequisites

| Requirement | Version / notes |
|---|---|
| Node.js | 20.x (the Lambda runtime is Node 20 — develop against the same major) |
| pnpm | 10.x (`corepack enable` or `npm i -g pnpm`); the repo pins `packageManager` in package.json |
| AWS account | With permissions to create CloudFormation stacks, Lambda, API GW, DynamoDB, S3, Kinesis, ECS, IAM roles |
| AWS CLI credentials | `aws configure` (or SSO). Region must match `sst.config.ts` → `eu-central-1` |
| A deployed search service | Any implementation of [search-service-contract.md](search-service-contract.md) |
| `cdb_stats` PostgreSQL | Optional but required for `/statistics` and the stats live-sync (a plain Postgres with the expected schema; the pipeline degrades gracefully if unreachable, statistics endpoints fail) |

```bash
git clone <repo-url> commonsdb-serverless
cd commonsdb-serverless
pnpm install
pnpm typecheck        # should pass with 0 errors
```

> `pnpm typecheck` needs the SST type declarations (`.sst/types`), which are generated by any
> `sst` command that synthesizes the app. If you get "Cannot find module 'sst/node/…'"-style
> augmentation errors on a fresh clone, run `npx sst build --stage staging` once.

## 2. Stages

SST deploys isolated copies of the whole app per **stage**. Conventions in this repo:

| Stage | Role | Notes |
|---|---|---|
| `dev` | Personal sandbox via `sst dev` (live Lambda) | Slack notifications are suppressed on this stage |
| `staging` | Shared integration environment | Integration tests run here |
| `cdb-b2b-api-prod` | **Production** | Deployed only via `./deploy-prod.sh` |

> **App/stage names are part of every CloudFormation stack name and physical resource name.**
> The app name is `commonsdb` (`sst.config.ts`); renaming it — or a stage — makes SST provision
> a *new, empty* copy of all infrastructure instead of updating the existing one. Note that the
> pre-decomposition production ran under a different app name: adopting this repository for that
> environment is a migration (fresh deploy + data/secret migration), not an in-place update.

## 3. Secrets

Secrets are stored in AWS SSM Parameter Store by SST and injected into Lambdas via bindings.
Set each one **per stage**:

```bash
npx sst secret set <NAME> <value> --stage <stage>
```

| Secret | What to put in it |
|---|---|
| `SECRET_SEARCH_SERVICE_API_KEY` | Shared key for the search service. Must equal the key the service expects in its `x-api-key` header. Generate: `openssl rand -hex 32` |
| `SECRET_SLACK_WEBHOOK_URL` | Slack incoming-webhook URL (`https://hooks.slack.com/services/…`) for ops notifications |
| `SECRET_ZUPLO_ACCESS_KEY` | Internal API key #1 — required in `x-api-key` by ingest + most search/lookup routes. In the gateway topology, the gateway injects it; generate any strong random string |
| `SECRET_ZUPLO_ACCESS_KEY_SEARCH_B2B` | Internal API key #2 — required by `GET /api/v1/search-iscc` (and accepted by `/statistics`) |
| `SECRET_IDENTIFIER_FIELD_KEY_NAME` | Name of the dynamic identifier field: `cidV1` (see [architecture.md §3.3](architecture.md#33-the-dynamic-identifier-field)) |
| `SECRET_TRUSTED_DECLARER_KEYS` | JSON object mapping declarer DID → PEM EC public key, used by ingest as a pinned-key fallback when a declaration JWT carries no embedded JWK. Use `_` to disable pinning (embedded-JWK verification still applies) |
| `SECRET_VALIDATION_BYPASS_DECLARERS` | Comma-separated declarer ids allowed to skip strict ingest validation (consistency + signature checks). **Use `_` (none) unless you operate legacy test declarers** |
| `SECRET_SLACK_NOTIFY_RULES` | JSON array of per-key Slack notification rules (`{"key","block"?,"rateLimit"?}` — see `notifyUtil.ts`). `_` = no per-key rules |
| `RANDOM_DECLARER_ID_DENYLIST` | Comma-separated declarer DIDs excluded from `GET /random`. `_` = none |
| `SECRET_ENCRYPTION_KEY` | Symmetric key used to encrypt customer keys at rest in the `customerKeys` table |
| `SECRET_CDB_STATS_PG_URL` | Postgres connection string for `cdb_stats`, e.g. `postgres://user:pass@host:5432/cdb_stats` |

A deploy fails with an explicit error if any bound secret is missing for the target stage.

## 4. Parameters

Non-secret configuration is defined **in code** (`stacks/CommonsDBStack.ts`) as
`Config.Parameter` values, some per-stage. Review these before the first deploy:

| Parameter | Default | Action needed |
|---|---|---|
| `SEARCH_SERVICE_URL` | `https://REPLACE-WITH-SEARCH-SERVICE-URL…` | **Required:** set to the base URL of the search service query API (no trailing slash) |
| `SEARCH_INDEX_STREAM_NAME` | `<stage>-commonsdb-serverless-search` | Kinesis index stream of the search deployment — matches its default naming, so usually no change; `_` disables indexing events |
| `ISCC_HOST` | placeholder | Set to your `iscc-web` service URL — used only by `GET /generateIsccFromUrl` (ISCC code generation) |
| `MIN_DECLARATION_TIMESTAMP` | `2026-01-09` | Earliest accepted declaration timestamp |
| `DECLARER_ID_DENYLIST` | `_` (no-op) | Comma-separated declarer DIDs excluded from search results |
| `IROH_REGISTRY_STREAM_NAME` | prod stream on `cdb-b2b-api-prod`, else `_` | `_` disables registry mirroring |
| `CDB_STATS_DYNAMO_TABLE` | `cdb_processed_declarations` | De-dup marker table of the external stats pipeline |
| `VERSION`, `KINESIS_SHARD_ID`, `DYNAMO_MILVUSMAP_*` | — | Leave as-is |

The full catalogue with consumers is in [configuration.md](configuration.md).

## 5. Deploy order for a brand-new stage

1. **Deploy the search service first** (separate deployment implementing
   [search-service-contract.md](search-service-contract.md)) and note its base URL. Configure it
   with the same shared key you will store as `SECRET_SEARCH_SERVICE_API_KEY` here. Its stack
   provisions the Kinesis index stream `<stage>-commonsdb-serverless-search` that this registry
   emits to — deploy both apps with the same stage name. Also make sure
   its index exists (see the contract doc and the service's own setup docs).
2. Edit `SEARCH_SERVICE_URL` (and `ISCC_HOST` if applicable) in `stacks/CommonsDBStack.ts`.
3. Set all secrets for the stage (§3).
4. Deploy:
   ```bash
   npx sst deploy --stage <stage>
   ```
   The first deploy also creates the SST bootstrap stack and takes considerably longer.
5. Record the stack outputs (printed at the end): `API_ingestApi`, `API_searchApi`,
   `API_customerKeysApi`, table names, `hostedISccDocker` (ISCC generator ALB).
6. **Smoke test:**
   ```bash
   # health of the search wiring (expects data only after the first ingest)
   curl -H "x-api-key: $ZUPLO_KEY" "$API_SEARCH/api/v1/fullCount"

   # submit a test declaration (see docs/api.md §Ingest for the payload format)
   curl -X POST -H "x-api-key: $ZUPLO_KEY" -H "content-type: application/json" \
        -d @declaration.json "$API_INGEST/api/v1/ingest"

   # poll status until "success"
   curl -H "x-api-key: $ZUPLO_KEY" "$API_SEARCH/api/v1/getDeclarationStatus?cidV1=<identifier>"

   # similarity search round-trip
   curl -H "x-api-key: $ZUPLO_KEY" "$API_SEARCH/api/v1/search?iscc=<the same ISCC>"
   ```

## 6. Day-to-day commands

```bash
pnpm dev:stag            # sst dev against staging: live Lambda, logs in terminal
pnpm typecheck           # tsc across the workspace (CI gate)
pnpm build               # sst build (synth only, no deploy)

./deploy-staging.sh      # guarded deploy: refuses dirty working tree, offers push, deploys staging
./deploy-prod.sh         # guarded deploy to cdb-b2b-api-prod with confirmation

npx sst console --stage <stage>   # SST web console (invocations, logs, resources)
```

## 7. Tests

```bash
# unit tests (Vitest) — offline, run from the repo root across workspaces
pnpm test                 # plain `vitest run`, no SST bindings needed

# integration tests (Jest, real HTTP against staging — never point them at prod)
cd integration-tests
cp env.template .env      # fill in API_BASE_URL (a deployed endpoint) + API_KEY
npm install
npm test                  # serial (--runInBand); the live smoke test skips without API_BASE_URL
```

## 8. Teardown

```bash
npx sst remove --stage <stage>
```

Note: the S3 declaration bucket is versioned and will block deletion while non-empty; empty it
manually first if you really intend to destroy a stage.

## Quick reference

```bash
pnpm install && pnpm typecheck
# search service deployed elsewhere → URL into stacks/CommonsDBStack.ts (SEARCH_SERVICE_URL)
for s in SECRET_SEARCH_SERVICE_API_KEY SECRET_SLACK_WEBHOOK_URL SECRET_ZUPLO_ACCESS_KEY \
         SECRET_ZUPLO_ACCESS_KEY_SEARCH_B2B SECRET_IDENTIFIER_FIELD_KEY_NAME \
         SECRET_ENCRYPTION_KEY SECRET_CDB_STATS_PG_URL SECRET_TRUSTED_DECLARER_KEYS \
         SECRET_VALIDATION_BYPASS_DECLARERS SECRET_SLACK_NOTIFY_RULES \
         RANDOM_DECLARER_ID_DENYLIST; do
  npx sst secret set $s <value> --stage staging   # "_" disables the optional ones
done
npx sst deploy --stage staging
```
